First inspect the existing scaffold and preserve its architecture.

Create clean, strongly typed contracts/models for the following concepts:

1. PaymentEvent
Represent a single payment event with fields needed for fraud-spike analysis, including:
- unique payment/event ID
- merchant ID
- timestamp
- amount
- currency
- payment method/type
- payment status
- customer identifier (privacy-safe/non-PII representation)
- device identifier (privacy-safe representation)
- geographic information at an appropriate coarse level
- fraud label where applicable
- metadata needed for future feature engineering

2. FraudLabel
Clearly distinguish:
- legitimate
- fraudulent
- unknown/unlabeled

Do not assume that every payment is labeled.

3. FraudSpikeIncident
Represent a detected fraud-spike incident, including:
- incident ID
- merchant ID
- detection timestamp
- analysis window
- baseline fraud rate
- observed fraud rate
- deviation/change
- affected transaction count
- severity
- status/lifecycle
- detector version
- confidence where applicable

4. EvidenceItem
Represent structured evidence used during an investigation, including:
- evidence ID
- incident ID
- evidence category
- metric/value
- baseline/comparison value where applicable
- supporting transaction/event references
- timestamp/window
- evidence strength/confidence where appropriate

5. Investigation
Represent an investigation associated with an incident, including:
- investigation ID
- incident ID
- status
- start/end timestamps
- hypotheses
- evidence references
- verification result
- confidence
- explanation
- recommended defensive response

6. EvaluationResult
Create a contract for genuine model evaluation containing:
- evaluation ID
- dataset/version identifier
- held-out test-set identifier
- detector version
- true positives
- true negatives
- false positives
- false negatives
- precision
- recall
- F1
- false-positive count
- false-positive cost
- evaluation timestamp

IMPORTANT:
Metrics must be nullable/absent until actually calculated.
Do not put placeholder values such as 99%, 95%, etc.

7. AuditEvent
Represent an immutable audit-log event including:
- event ID
- timestamp
- event type
- actor/source
- incident/investigation reference where applicable
- action
- structured details
